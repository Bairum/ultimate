# Faux demo

Send `questions demo` to preview the questions card: a yes/no question and a choice with a recommendation.
`decisions demo` sends three lettered decisions with stated picks (read without a model); `ask <text>` sends any text
as a reply-expected message to the user.
In @ultimate's conversation, send `messages demo` to send the user a one-way update and a question, or `message #<id>` or `message @<name>`
(optionally `one-way`) to message another conversation, previewing the outgoing message cards; paste images with it to forward them (`images: 'latest'`).
In @ultimate's conversation, `chat demo` (typed, or posted to @ultimate) runs tools, starts a `landing demo` branch
that reports a landing back, and sends you a one-way update and a question; `ask demo` asks another question in a message. A reply
from another conversation gets a short acknowledgement.
In @ultimate's conversation, `cards demo` produces one of each card its chat folds to one line: it starts a
`landing demo` branch, messages it, calls the `seedCards {from}` action through codemode (messages, a reply, a report,
notes, a catch-up, finished, a post-compaction wake-up, an abstract, a lander report and a landing note, display only),
then sends you an update and a question, which stay open.
Under faux, summaries run on scripted neutral responses unless `summaryModel` is set. Their title and Ask line
come from the latest user prompt, with generic demo summary, feature and activity text (a prompt containing `no feature` leaves the feature unset, to
preview a conversation shown by its title); only the questions demo
reply is assessed as needing input. The default model is `faux/faux-1`, so assessment and extraction exercise the
same durable flow as real replies without external model calls.

Onboarding is scripted too: `onboarding.start` greets and shows applicable extensions, project and git `setup` cards,
one at a time. Each `onboarding.choice` advances it; after the last it calls `read` on the project's README, then
`remember` with a canned project memory plus the user's instructions verbatim as a memory, and asks **What should we do first?** A subsequent
input to @ultimate calls `branch` in shared mode (so the demo also works without Git). The demo does not initialize
Git or invent project-specific integrations; the real agent's instructions cover those judgment calls.

Development-only scripted responses for `ULTIMATE_FAUX=1`. Inert without `host.faux`. The core supplies Pi's faux provider; this extension supplies the looping shell/edit, codemode, restart, subagent, `submit workspace` (a `workspace submit` call), `leave a note` (a `note` to the root), the `seedLandings {from}` action (five demo landing notes with real-looking shas, features and commit counts in `from`'s root, to preview the Landed section), the `seedMemory {root?, op?}` action (twelve memories of every kind and age in root `root`, 1 by default, to preview the root's Memory fold; `op: 'update'` rewrites `pi-durable-pinned`, `op: 'delete'` drops `worktree-cleanup-race`), the `seedFlights` action (two isolated branches of root 1: one with three commits and an uncommitted edit, one with only uncommitted edits, to preview the In flight rows' work), the `seedEvents {from}` action (durable events about `from` and its root: the root, the branch, five landings, two warning notices, and `cloud.backup` events in each phase, a refused one among them, to preview the Activity panel and the System stream; the landings also reach the root as landing notes), the `seedLanes` action (a team next to @ultimate and the lander: two coordinator branches, one with two workers and a reviewer with two sub-reviewers, the other with one forked worker, with half an hour of their tool and model calls written into `trace.sqlite`, one failing, their `subagents.started` and `board.sent` events written into the event log with past times (exact spawn calls, inferred ones, and messages between them), and one worker still calling every 3 s for an hour, to preview the System surface's Agent Lanes and their hierarchy), the `seedCodemode {conversation}` action (or the prompt `seed codemode`: a run of @ultimate's real codemode calls between bash and read steps, with their summary lines, to preview codemode cards and folded runs), `codemode steps demo` (live codemode calls, read-only, writing and failing, which the faux summary model summarizes), the `seedContext {from}` action (in a conversation that has run once: a reviewer subagent whose first request carries 15 of its prompt sections and two tools, and in `from` a mid-conversation prompt patch that changes, adds and removes sections and tools, to preview the context header and its diff marker), the `seedHistory {conversation, count}` action (about `count` entries, 1000 by default, in turns of a user input, a tool call, its result and a Markdown answer, to preview a long transcript and its scrollback), `notify <id>` / `notify <id> quietly` (a `notify` call), `screenshot <file>.png` (a `screenshot` saved at that path), `phases demo` (a slower explore, edit, test and commit sequence for previewing working states; the commit is real, in `demo.txt.git` in the instance home, so it records `coding-tools.committed`) `long bash demo` (a five-minute polling bash call, to preview cancelling one) and `fail demo` (a provider error that fails the run) and `delegate demo` (two workers: one answers, one fails, to preview subagent states) demos, answers lineage's compaction requests with a short distillation, and creates `demo.txt` only in the instance home. Without this extension, a caller can queue its own responses on the faux handle; Pi reports an error if its response queue is empty.
