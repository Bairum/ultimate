# Cloud sync

An optional machine-side replica sender, inert until configured. With a URL and token it opens one outbound WebSocket, sends conversation records, own entries and conversation documents, then streams committed changes. Reconnects compare each conversation's newest own entry ID and document hashes. Catch-up streams entries and documents page by page, waiting for room in the four-batch acknowledgement window before reading more; history reads do not hold Pi's commit line. Session and task documents stay local. Pending records and buffered changes share a fixed 16 MiB retained-data limit; crossing it closes the socket, discards the buffers, and reconnects with the normal backoff to resume from the replica's durable cursor. During catch-up, document and conversation changes retain only IDs, not intermediate values.

Configure once in **user** settings (`~/.ultimate/settings.json`):

```json
{ "cloud": { "url": "wss://example.com", "machine": "my-machine" } }
```

The sender connects to `/sync/v2` on that host; a path in the URL is ignored.

Add `ULTIMATE_CLOUD_TOKEN`, the endpoint's bearer token, in the Secrets panel (⌘K → Secrets). `machine` is optional and defaults to the OS hostname. Project settings are never read: a repository cannot redirect the user's history to another server. Configuration is read when the extension loads; restart after changing it. Two more user settings time the lease: `cloud.idleRelease` (idle minutes before the writer releases, default 10, `0` never) and `cloud.autoClaim` (a starting machine takes a free lease by itself, default true).

Environment overrides take precedence, for process-scoped experiments:

- `ULTIMATE_CLOUD_URL` overrides the user URL.
- `ULTIMATE_CLOUD_TOKEN` overrides the secret.
- `ULTIMATE_CLOUD_MACHINE` overrides the user machine name.

Faux hosts and preview instances stay silent and do not sync from user settings. An explicit `ULTIMATE_CLOUD_URL` enables them for local experiments (with a token from the environment or Secrets). Previews strip all three cloud environment variables inherited from their parent. A configured URL without a token produces one notice naming the missing secret, and no connection.

A project is its GitHub repository (`identity.ts`): the `origin` remote normalised to `github.com/<owner>/<repo>`, lowercased, plus the oldest root commit as a sanity check. Every checkout of it, on any machine, connects to the same replica with `/sync/v2?project=<key>`. Without a GitHub origin the host does not sync and notices once: `Cloud sync is off: <root> has no GitHub origin remote.`

Hello carries the key, root commit, project root, machine name, HTTP port, the lease epoch from `<home>/cloud-lease.json` (absent when it holds none), whether local storage has history, and the names (never values) of the user's secrets. Every five seconds the sender compares the names in the user's store with the ones it last sent and, when they changed, sends `{ type: 'secrets', secrets, secretsComplete }`, as a writer and as a standby, so another machine's missing secrets refresh without a reconnect. The cloud answers `role`. As the writer the host rewrites `cloud-lease.json` with the epoch it is given, then builds and uploads its UI, sends metadata and catches up as below. As a standby it sends nothing more and keeps the socket only to follow role updates (writer, online state, a free lease); a role that changes on an open socket starts over with a fresh hello. `syncState()` returns the last role, epoch, writer and lease state for other code in the process. A different root commit is refused with close code `4009`; the host reports it, suggesting `cloud.relink` for a renamed repository, and stops retrying. The cloud directory at `/` lists one row per project, linking to a stable `/p/<repo>/` URL with live requests through the writer's port and offline history while it is stopped. Empty summary lists during host opening/closing are ignored, preserving the last non-empty list.

For live routing, the deploying user's `cloud.tunnels` maps exact machine names to tunnel IDs: `{ "cloud": { "url": "wss://example.com", "tunnels": { "my-machine": "<tunnel-id>" } } }`. This replaces `cloud.vpcService`. Adding a machine means creating/running its tunnel, adding that map entry, and deploying again; extra projects/ports need no new bindings. Without a matching machine binding the replica is offline-only. See `cloud/README.md` for setup and local two-host verification.

System info is compared once a second, ignoring `machine.freeMemory` and the SQLite `persistence.sizeBytes`/`walBytes` counters. Meaningful changes (including build and extensions) send immediately; a full snapshot also refreshes every 60 seconds so volatile Info values are at most a minute stale. Each connection sends the full non-empty summary list once; subsequent messages contain only changed summaries and removed conversation IDs. An empty host conversation list is ignored during opening/closing, as an open host always has its root. If the oldest unacknowledged batch exceeds 60 seconds, the sender raises one `Cloud sync stalled: no acknowledgement for 60 s; reconnecting` notice, closes the socket and resumes through the normal reconnect/cursor path. A connection that had been open for 10 seconds and drops, as a deploy restarting the replica does, reconnects at once; backoff applies from the next failure on.

The same connection also publishes a per-project production UI build, including trusted enabled project web facets. The host checks a source fingerprint every five seconds, waits 60 seconds of quiet after changes, and runs at most one low-priority Vite child at a time. It uploads only R2 files reported missing, using the same bearer token in an Authorization header. The cached build lives in the instance home; the replica and Directory retain its content-hashed `uiBuild` while offline. Cloud HTML and build assets are behind the Worker's JWT check, and a changed UI build triggers the existing reload notice. See `cloud/README.md` for the shared-asset layout, limits, bucket setup and retention policy.

`snapshot.ts` moves a project between machines through the cloud's private R2. `uploadSnapshot` copies the database consistently with a read-only `VACUUM INTO` (an open database's committed WAL included), bundles the `ultimate/*` branches when there are any, compresses both with zstd and uploads them in chunks of at most 16 MiB, then an encrypted manifest with each part's plaintext SHA-256, size and chunk count. Every object is AES-256-GCM with a random nonce, under a key derived per snapshot with HKDF-SHA256 from the `ULTIMATE_CLOUD_SNAPSHOT_KEY` secret (the same value on every machine), salted with the project key; the associated data names the snapshot, part, index and whether it is the last chunk, so altered, reordered, swapped or dropped chunks, another secret and another project all fail verification. `downloadSnapshot` verifies and writes `<dir>/snapshot-<id>.sqlite`, checks its integrity, and adds the branches without force: new ones are created, older ones fast-forwarded unless checked out in a worktree, ones already containing the incoming commit stay, and any other keeps the local branch and stores the incoming one as `refs/heads/ultimate-moved/<id>/<name>` (returned as `keptRefs`). On failure it removes only its own files. `databaseHash` is the SHA-256 of the same `VACUUM INTO` copy, so an unchanged database hashes to its snapshot's manifest. Requests retry twice after network errors and 5xx answers.

`lease.ts` makes a machine run the project only while it holds the lease, driving core's standby switches (`host.deactivate`/`host.activate`) from the roles it hears. Roles are handled after a `setTimeout(0)`, one switch at a time, never inside a socket handler or tool run. A standby connection sends only hello and lease messages and ignores `cursor` and `outbox`; the writer reconnects with a fresh hello once storage is open.

- **Join.** A home whose `cloud-lease.json` does not name the project (new, or with a database the cloud never admitted) writes `standby.json` `{ reason: 'Waiting for the cloud', joining: true, cloud: true }` when the facet loads, before the server opens storage, and stays on standby until the cloud names its role, however long that takes: a machine the cloud did not admit never writes. As a standby it opens no database; as the first machine of a new project the cloud registers it as the writer and it opens its database, the existing one or a fresh one, in place. Only the last writer, whose lease file names the project, opens storage while the cloud is unreachable; a stale one is fenced off on reconnect and returns to standby.
- **Standby.** A serving machine told it is a standby closes storage with standby info `{ reason, writer, free, cloud: true }`. Its database stays in place when it is the lease's last snapshot (`cloud-lease.json` names that snapshot and its epoch, and `databaseHash` matches the recorded `snapshotHash`); otherwise it is parked, with its `-wal` and `-shm`, as `state.stale-<ISO time>.sqlite`. No database is ever deleted.
- **Release.** The writer releases after `cloud.idleRelease` idle minutes (no foreground task, so no conversation or lander run, and no automation due within that time), when a standby asks, and on a clean stop. It closes storage, uploads a snapshot, records `{ key, epoch, snapshot, snapshotHash }` in `cloud-lease.json`, sends `release` from a standby connection and waits for the free lease. An idle release stays on standby as "Released · resume here". A release for a move writes "Moved to <machine>" with `explained: true`, so the standby page leaves out that subtitle and the facet's sentence ("The project moved to … Move here pulls it back …") says it once. A failure before `release` was sent keeps the lease and serves again; a release sent but unconfirmed waits for the cloud's next role. Asked by a standby, the writer holds the release, however long, while foreground tasks run and then while worktrees hold uncommitted changes; no agent decides when. It rechecks on every task graph change and every 30 seconds (`HOLD_RECHECK`), and reports each change of what it waits for with `release-waiting` and the notice "Move to <machine> waits for N running tasks" (or "… N worktrees with uncommitted changes") on both machines: the count and the conversations (`runs`, `#12 title`), then the dirty worktrees (`dirty` with `held: true`). @sync, which may have asked, runs in the machine home's own process, so its run never counts. A move started with `force` skips both holds and releases at once. If that transition ends meanwhile (failed or cancelled), it stops waiting and keeps the project. Idle checks pause while a move holds.
- **Clean stop.** The process cleanup (not a facet reload) releases within the supervisor's ten-second shutdown: it closes storage if it is still open, takes the storage lock (failing that, a swapped-in core owns storage and nothing is released), writes `standby.json`, then uploads and releases within eight seconds. If nothing was released it removes `standby.json` again, so the next start opens normally and still holds the lease.
- **Move.** A standby takes the lease on start when it is free (`cloud.autoClaim`, recorded as `by: 'auto'`), with `moveHere` (`by: 'local'`, or `'sync'` when @sync calls it), or when the cloud UI or @sync's bearer route sends `move-to` (`by: 'cloud'` or `'sync'`). It first prepares, and reports every step to the cloud as a `Transition` (`cloud/README.md`), at once on each step change and at most twice a second for download progress:
  1. `fetch`: `git fetch origin`, then fast-forward the checkout's branch to `origin/<default branch>`. Refused when tracked files have changes, the checkout is on another branch or detached, or the branch has diverged. Its detail says `main fast-forwarded 2 commits, 3779f5b..34596c0` with the count in `commits`, or `main already up to date`.
  2. `install`: `pnpm install --frozen-lockfile` (no shell, nothing streamed, the end of its output on failure) while one is owed: `cloud-install-pending` in the home is written before a fast-forward that changes `pnpm-lock.yaml` and removed only after an install succeeded, so a crash or a failure in between installs on the next try.
  3. `checks`: the root guard (the writer's project root must be this checkout's), an online writer or a free lease with a snapshot, `ULTIMATE_CLOUD_SNAPSHOT_KEY`, a model login, and the writer's secret names this machine lacks, which fail the step unless the move was started with `force`. The model login (`login.ts`) is the default provider's (`defaultProvider` in Pi's settings), or without one any provider with an available model, as the root conversation picks: it must have configured credentials (stored, runtime or from the environment), as the login panel shows them; no provider is called, but a configured provider whose latest call on this machine failed (`~/.ultimate/health.json`, see `extensions/health`) does not count. Without it the step fails with `No model login: <provider> is not configured here; log in with ⌘K → Log in`, or for a failing provider `<provider> is failing here: <error>; log in again with ⌘K → Log in`, also with `force`.
  4. `handover`: when the writer holds the lease, `request-release` (with `force` when the move was forced), then wait for the free lease; skipped when it is free. While runs drain the step's detail says `finishing 2 runs` and the transition keeps their conversations as `waiting`. Once they drained the writer lists the worktrees of its checkout, the main one included (`git worktree list --porcelain`), whose `git status --porcelain` is not empty (at most 20 paths of 500 characters), so edits the drained runs made count too. Unforced, it holds until they are clean: the detail says `waiting for 2 worktrees with uncommitted changes` and the transition keeps them as `left`, cleared once committed. Forced, they stay on that machine: `2 worktrees with uncommitted changes stay on haza-pc`. A check that fails (listing the worktrees, or the status of one that is not `prunable`) holds an unforced move too, with `unchecked` and the detail `could not check worktrees: <error>`, and is retried like a dirty one; a forced move releases anyway. A run that starts during the check sends the move back to waiting for runs.
  5. `download`: the snapshot into the home, with bytes done and total, unless the local database is that snapshot.
  6. `branches`: the `ultimate/*` branches `downloadSnapshot` restored, naming the refs it kept aside.
  7. `claim`: send `claim`; on `writer`, open storage after parking any local database as stale and renaming the download to `state.sqlite`.

  A failure, or a cancel before the claim is sent, ends the transition with its `error`, deletes only the download, and leaves the holder and the local database as they are. A cancel during the handover makes a draining writer keep the project; one that already released leaves the lease free. So does the cloud ending the transition because a machine in it went away.

  Before sending `claim` the machine writes `cloud-claim.json` (`{ key, epoch, snapshot, download?, hash }`), and while it exists its hello names the claimed epoch + 1. On standby, every role is checked against an intent first: the writer at that epoch finishes the claim (the download installed if it hashes right, fetched again otherwise, unless the local database already is the snapshot), anything else drops the intent and its download. Once the claim won, a failure to open storage (parking the local database, renaming the download into place, opening) keeps the intent and the download for that recovery. A claim sent on a connection that dropped is answered by the next connection's first role, which follows a hello naming the claimed epoch + 1: the writer's role means won, any other lost. Snapshots use the replica's key from `role.project`, not this checkout's, so a relinked machine takes over too. Transition details and errors are bounded to 500 characters, keeping the end. Without an intent, `writer` on standby opens the local database only when it is the writer's state (the lease file's epoch, the last released snapshot, or no snapshot yet, as for a project this machine just registered); otherwise it installs the last snapshot first. A standby connection never rewrites `cloud-lease.json`; opening storage as the writer does. On start, `.snapshot-*` temp folders and downloads no intent owns are removed. See "Guarantees" in `cloud/README.md`.

Actions: `state` returns `{ status, machine, role, free, writer, missing, blocked, progress, transition, ran, key, sync, login, lastError }` (`types.ts`), where `login` is `{ provider, ok, error? }`, the model login the checks step requires, where `ran` is the last move this machine ran itself (also once a newer one shows as `transition`), `key` the replica key the cloud admitted this machine under (after a relink, not its origin's), and `status` is `off` without cloud configuration, `local` for a project without a GitHub origin and `on` otherwise, `machine` is this machine's name, `missing` lists the writer's secret names this machine lacks, `blocked` says why "Move here" cannot work, `progress` is a release's upload and `transition` the move this machine runs or the latest the cloud reported. `sync` is the connection as operators watch it: `{ connected, catchingUp, backlog, lastAckAt?, conversations?: { synced, total } }`, where `backlog` counts unacknowledged batches plus the conversations catch-up has not reached yet. User-only `moveHere { force?, by? }` starts a move and returns its `{ id }` at once, recorded as this machine's page unless `by: 'sync'`; user-only `cancel` stops it until its claim is sent. User-only `relink { from }` asks the Worker (`POST /sync/relink`) to sync this checkout's key to the replica of `from` from now on, after a repository rename or a root-commit mismatch, forgets a lease epoch held under the current key, and reconnects. Relink every machine of a renamed project, or update its remote, before moving it: snapshots are keyed by the key each machine connects with.

The idle check runs every minute, or four times within a shorter `cloud.idleRelease` (fractions of a minute are allowed, for tests).

The web facet (`web.tsx`) shows where the project runs and moves it. Locally it polls `state` (every second while a move runs) and acts with `moveHere` and `cancel`; at `/p/<slug>/` in the cloud it polls the replica's `GET /api/cloud` instead and moves with `POST /api/cloud/move|cancel`, which work while the writer machine is off.

- **The move's card** (`transition.tsx`): its title by phase ("Preparing rog", "Handing over: haza-pc finishing 2 runs", "Running on rog", or failed) with who started it ("· started from the cloud UI", "· by @sync", "· from rog's page", "· automatically"), a line per step with its state and detail, an arrow with the commit count on a fetch that fast-forwarded, the conversations a handover waits for and the worktrees it waits for or leaves with uncommitted changes collapsed under the handover line, the download's megabytes with a thin bar, Cancel while it can be cancelled, and "Continue anyway" when the checks failed only on missing secrets (`force`). A failed move stays until dismissed or the next one starts; a finished one shows on the pages that watched it run.
- **Standby page** (`standby` slot): who runs the project, the secrets this machine lacks, why it cannot move, **Move here** (**Resume here** for a lease this machine released), and the card. On the machine the project moved away from (its finished move left from here, or its standby reason `Moved to <machine>`), a note says what **Move here** does: "The project moved to haza-pc (by @sync · 13:51). Move here pulls it back to rog." The status-line popover shows the same note.
- **Status line**: `on haza-pc`, `standby · runs on rog`, `free`, or `local only`; nothing without cloud configuration. Its popover lists the machines with **Move here** and, while the writer catches up, a quiet `Catching up 120/537 conversations` line, or in the cloud every machine the replica knows (running, standby with a checkout, not connected, missing secrets) with **Run here**.
- **Banner** (`conversation.overlay`): the card on a serving writer while a move to another machine runs, and in the cloud during any move, or while no machine serves the project, "Run on…".

The cloud implementation and shared wire contract live in `cloud/`. Prompts queued there are submitted locally with the outbox UUID as Pi's `requestId`, so retries admit one submission. Unknown conversations produce a notice and leave the item undelivered. Closing the host closes the socket; failed connections, including a Worker that does not serve `/sync/v2` yet, retry with a 1–30 second backoff.
