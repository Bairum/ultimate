Ultimate's awareness of its own code: the replay-safe `restart` tool requests a type-checked blue/green core swap from the supervisor (`pnpm start`). Failed preparation returns diagnostics while the old core continues. Before storage is released, the tool records the next generation in its task memo; replay in the new owner returns the running generation and pid.

Call after changing `server/` or `shared/`, only when shared-host application is authorized. Never call for `web/`, `extensions/`, or `agents/`: those reload without a core swap.

From an isolated top-level main, deliberately use `restart {applyHost: true}` only after verifying workers → own workspace → captured original checkout/branch. Core-owned `workspaces.proveHostLanding` must prove a ready/active main workspace, correct own branch/cwd, unchanged captured non-null target branch, clean own and destination, and exact own tip = recorded landed tip = source tip in the actual running Ultimate checkout. Unlanded/new commits, dirt, unknown workspaces, workers/forks, other hosts, changed branches and moved source refuse before memo/restart effects. Core proof reserves own/destination in the durable lifecycle queue, refuses same-source pending mutations, and blocks new related execution/lifecycle admission through the restart checkpoint. Approval rechecks the pinned proof and checkpoints handoff before memo write. Preparation failure/pre-approval cancel releases it; approved caller stop stays pinned until storage reopen, and active replay/rollback releases the resumed reservation. The factory requires the full core proof capability eagerly; absent/partial core leaves the previous facet installed. Normal host-root restart, approved replay and activation rollback remain unchanged. No duplicate restart tool or raw-POST workaround for isolates.

Restart swaps the shared host for all conversations. Landing never restarts automatically; supervisor-owned rollout restrictions still require a coordinator/user grant. Report ready or a concrete apply blocker instead of an unauthorized restart or Done at an intermediate branch. `POST /api/restart` requests the same swap and returns an accepted generation before handover; reconnect to `/api/events` to observe readiness.

`web.tsx` shows the same in the UI: the `restart` call from its `details` (generations, builds, rollback, or the boot error), a "core changed — restart" header badge while `system.code.coreStale` that swaps through `api.restart()`, `build <id>` in the status line with its components and recent history, and a "Reloaded · build a → b · changed: …" marker in the transcript where the build section of the prompt changed, a quiet "Restarted · gen 3 → 4 · same build" where only the generation did (an entry renderer for `pi.system` that falls back to the core divider).
