Delegate bounded work with `subagent`: `start {agent, task, background?, fork?}`, `message {id, text, steer?}`, `wait {id}`, `stop {id}`, and `list`. Foreground children belong to the tool call; background children belong to a background anchor and their answers steer the current run at its next tool-round boundary, or start a run when the parent is idle. Child IDs are conversation IDs. Definitions are reread on every start; children never receive `subagent`.

Definitions are Markdown with YAML frontmatter, parsed by Pi's `parseFrontmatter`: required `name` and `description`, optional `isolate` (`none` or `worktree`), `model` (Pi's `resolveCliModel` accepts `provider/id`, fuzzy id or name, and a `:thinking` suffix; unknown models are errors and custom models must be registered in Pi's `models.json`), `thinking` (a Pi thinking level), and `tools` (a YAML list, `[read, bash]` or one `- item` per line); other fields are errors. An explicit `thinking` field overrides the model suffix. The body is the instructions. `agents.ts` reads them from three directories, later overriding by name: `agents/` in Ultimate's clone, `~/.ultimate/agents/`, and the project root's `.ultimate/agents/` (not a conversation's cwd). Omitted tools inherit the parent's tools minus `subagent`. Tool restrictions select tools, not a shell sandbox: read-only agents' bash restrictions are instructions. An edited definition is not a code change, so it does not change the build id.

## History forks

`start {agent, task, fork: true}` gives the child the parent's visible history up to the entry before the assistant message containing this call, excluding the pending call itself. The task text is still the child's first new input. Foreground/background ownership, definition instructions, model, thinking, tools (never `subagent`), and isolates work exactly as for a fresh child.

A fork sends the parent's context and therefore costs more than a fresh child; the prompt cache usually covers the shared prefix. Conversation documents follow their declared fork policy: `pi.agent`, `codemode.store`, and `ultimate.ui` copy `asOf` the fork entry; `ultimate.subagents`, `ultimate.metadata`, `models.login`, and Pi's inbox, live state and usage start `initial`. No built-in conversation document uses `current`. The child agent configuration is then replaced with the current parent's configuration and definition overrides; metadata is set to the child's name/task. The child's `ultimate.ui` copy is left as-is: the web reads only the root conversation's UI document, so the unused child copy cannot affect the Agents tab. Its Subagents index starts empty. Codemode's stored values remain available as of the fork point.

## Isolates

An isolate is where a child's tools run, separate from the parent. Worktree is the first, local kind; sandboxes, containers, Cloudflare, and remote machines are not implemented. Each kind lives in its own module with create, land and discard operations, without a registry or plugin API.

`start {agent, task, isolate?: "none" | "worktree"}` overrides the definition's isolate. The default is none (the shared parent directory); the shipped worker uses worktree. A worktree is created before the child starts, on `ultimate/<agent>-<key>` from the parent checkout's HEAD, under the instance home's `worktrees/`. The child's cwd and instructions point there. Uncommitted parent changes are not included. The isolate and child are reused on replay.

Optional project `.ultimate/settings.json` configuration:

```json
{ "isolates": { "worktree": { "setup": ["pnpm install --frozen-lockfile --prefer-offline"] } } }
```

Commands run in order with `sh -c`, closed stdin and a two-minute timeout per command. `ULTIMATE_SOURCE` is the parent checkout path (for example, `cp "$ULTIMATE_SOURCE/.env" .`). A failure reports the output tail and removes the worktree. Setup is recorded so a completed setup is not repeated on replay.

Verify the child's commits, then `land {id}`: refuses a running child or dirty worktree, rebases onto the parent HEAD and merges fast-forward only. Conflicts abort the rebase and name files to resolve by messaging the child. Repeated landing is a no-op. Results list commits and paths, and flag Ultimate core changes that need restart. Lands into one parent checkout are serialized in-process. `discard {id}` refuses a running child, removes the worktree even if dirty, and keeps its branch and commits. Both operations are also extension actions for the UI, acting for the conversation the call names; `list` includes isolate records. The read action `isolate {parent, id}` returns a child's record with `ahead`, its branch's commits missing from the parent checkout (null once the branch is deleted), or null without an isolate.

Isolation is by working directory, not a sandbox: absolute paths can still reach other checkouts. Children are instructed to work only in their isolate, commit clearly, and never push. There are no remote operations, preview instances, or cross-process landing locks.

The shipped definitions inherit the active provider/model. No universally cheaper model is known across providers, so no model is hardcoded. Override locally to select an available fast model.

The extension document `ultimate.subagents` holds the ownership/action index. Each child gets the core's `ultimate.metadata` (`host.metadata`) with `label` set to its definition's name and `title` to its task, which the shell's header, breadcrumb, and window title show. Reporter request IDs and answer receipts prevent duplicate delivery across restarts; stop records its target run so a replay cannot abort a later run. The action `definitions` returns the definitions (without instructions) and the files that failed to parse, with their errors.

`web.tsx` renders each `subagent` call (agent, task or message, the child's isolate branch and state from the document, whether the child is working, its answer, and "open #id" to show the child; the result's details say whether the child is in the background) and adds the right panel's Agents tab: main and its subagents as a tree with working marks and, while a background child works, its `bg` mark from the owner task in the task graph. A child with an isolate shows its state (active, landed with a short sha, or discarded) and commits ahead in its row, and below it the branch with Land and Discard for the parent, disabled while the child runs; Discard asks first, and errors, landing results, and a needed restart show inline. Isolates refetch when the child or parent settles and when the window regains focus. Below the tree come the definitions with their model and thinking level, and invalid files with their errors, refetched when the window regains focus. Showing a child makes the composer steer, follow up, and stop that child; the header leads back to main.
