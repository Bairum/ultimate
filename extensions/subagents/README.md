Delegate bounded work with `subagent`: `start {agent, task, background?, fork?}`, `message {id, text, steer?}`, `wait {id}`, `stop {id}`, and `list`. Every new child belongs to an independent background anchor. Foreground is a waiting style, not lifetime ownership: foreground start/message and explicit wait return the answer when ready, or yield on queued steering while the child keeps running. Stopping the parent does not stop these children; use `stop {id}` explicitly. Stop cancels the captured current work and existing pending reporters/inputs, even before a child run starts; replay leaves later reuse alone. Undelivered answers steer the current run at its next tool-round boundary, or start a run when the parent is idle. Child IDs are conversation IDs. Definitions are reread on every start; children never receive `subagent`.

## Interruptible waits and delivery

A yielded wait returns status text, **not an answer**, with `details: { conversationId, yielded: true }` (and `background: true` for a background-style child). Message or stop that ID, or wait again. The wait observes the parent inbox's acquisition snapshot and updates; it never reads queued input content or places it. Follow-ups do not wake waits. Other children's answer reports do wake waits so the parent can act; an already completed answer from the awaited child takes precedence. Only local losing waits are canceled, never the child or parent. An unrelated long tool in the same round can still delay the normal boundary.

Before each model request, a compact reminder lists running children and durable inputs still pending before their child run starts. The reminder is refreshed from documents/tasks, not from prior tool results.

Start/message atomically install a reporter with their action record before waiting. Reporters claim each answer once and submit it with `subagent-answer:<answer entry ID>`. Successful answer results carry `details.answerId`. A nested result consumed by a script is not yet a model receipt: successful outer codemode results acknowledge answers through `details.subagentAnswers`; yielded/error results omit these receipts, leaving earlier answers queued rather than losing them when a sibling wait yields.

The subagents `afterTools` hook reads committed outer tool results before Pi's boundary and atomically withdraws only acknowledged, still-queued reports. It also records a settled request receipt when a reporter has not submitted yet, so a late submission is deduplicated by the same answer identity. Already placed reports are not withdrawn. Receipts and hook replay are idempotent across restart. `wait` can still return an already delivered answer on explicit request; exactly-once applies to automatic reports, not repeated explicit reads.

Definitions are Markdown with YAML frontmatter, parsed by Pi's `parseFrontmatter`: required `name` and `description`, optional `isolate` (`none` or `worktree`), `model` (Pi's `resolveCliModel` accepts `provider/id`, fuzzy id or name, and a `:thinking` suffix; unknown models are errors and custom models must be registered in Pi's `models.json`), `thinking` (a Pi thinking level), and `tools` (a YAML list, `[read, bash]` or one `- item` per line); other fields are errors. An explicit `thinking` field overrides the model suffix. The body is the instructions. `agents.ts` reads them from three directories, later overriding by name: `agents/` in Ultimate's clone, `~/.ultimate/agents/`, and the project root's `.ultimate/agents/` (not a conversation's cwd). Omitted tools inherit the parent's tools minus `subagent`. Tool restrictions select tools, not a shell sandbox: read-only agents' bash restrictions are instructions. An edited definition is not a code change, so it does not change the build id.

## Definitions are shared profiles

A definition is the profile both subagents and automations run with: one helper, `createChild` (`children.ts`) with `definitionAgent` (`agents.ts`), turns it into a child's agent configuration for `start` and for an automation that names it. Edit one in the Agents tab or as its file; both are the same Markdown, and Ultimate changes one when asked by editing that file (codemode's `ultimate.agents()` lists every definition with its source, path, and fields). Built-ins in the clone are never written: saving one writes an override with the same name to the project's `.ultimate/agents/` (shared with the team, and only once the project's setup is local) or to `~/.ultimate/agents/`. Deleting an override makes the definition it shadowed apply again.

Click a definition in the Agents tab, or New, for its config view: description, model (picked from the models extension's catalogue, or inherited from the main conversation), thinking (the levels that model supports, or inherited), tools (a checklist of the main conversation's tools, or all of them), isolate, and the instructions as Markdown with a preview and the saved file. The header shows its source and path, the footer where Save writes and whether that overrides or is shadowed by another file. Duplicate starts a new definition from the shown one. Save writes nothing when the result fails to parse, and shows why inline; files that fail to parse stay listed with their errors and open with the error above the form. Another extension opens a definition's config over the web bus with `events.emit('subagents:open-definition', { name })` (`''` for a new one); `subagents:definition-closed { name }` follows when that dialog closes, so the opener can refetch and take focus back.

## Coordinator flow

The extension's prompt section makes the parent the coordinator; without this extension, that steering is absent. Do quick fixes and simple questions directly. For substantive work, inspect the code, recommend one approach, and ask only for decisions affecting behaviour or scope. Use the `plan` tool to write an epic with binary acceptance criteria and one self-contained task per unit of work; link children and record dependencies and status.

Delegate implementation to `worker` in worktree isolates and bounded reconnaissance to `scout`. Use background children for independent work; children touching the same files run sequentially. Read each report, inspect its isolate's commit diff, and rerun meaningful checks yourself before landing. Land, reload (or `restart` for `server/` and `shared/`), and rerun meaningful checks in the parent after the last land of a batch. Discard landed isolates when their children have no further work. Record evidence and mark tasks done yourself; an idle child or a child's check report is not verification.

When all tasks are done, run every definition whose name starts with `reviewer` in parallel on the same explicit `base..head` commit range, never merely a directory. Merge and verify findings yourself, route confirmed fixes back by message or a new task, and verify, land, and review fixes. Post the epic verdict and report to the user. Never delegate judgment. Heavy commands are serialized by `exclusive-commands`; do not bypass it. Children never push; the coordinator never pushes, merges to remotes, or ships unless asked.

### Add another reviewer

Copy `agents/reviewer.md` to `~/.ultimate/agents/reviewer-second.md`, keep its read-only contract and tools, change `name` to `reviewer-second`, and add `model: provider/model-id` using an available registered model different from the parent's. The shipped `reviewer` inherits the parent's model; the `reviewer*` naming convention includes both in the parallel review. Definitions are reread on every start; no restart is needed.

## History forks

`start {agent, task, fork: true}` gives the child the parent's visible history up to the entry before the assistant message containing this call, excluding the pending call itself. The task text is still the child's first new input. Foreground/background waiting style, independent ownership, definition instructions, model, thinking, tools (never `subagent`), and isolates work exactly as for a fresh child.

A fork sends the parent's context and therefore costs more than a fresh child; the prompt cache usually covers the shared prefix. Conversation documents follow their declared fork policy: `pi.agent`, `codemode.store`, and `ultimate.ui` copy `asOf` the fork entry; `ultimate.subagents`, `ultimate.metadata`, `models.login`, and Pi's inbox, live state and usage start `initial`. No built-in conversation document uses `current`. The child agent configuration is then replaced with the current parent's configuration and definition overrides; metadata is set to the child's name/task. The child's `ultimate.ui` copy is left as-is: the web reads only the root conversation's UI document, so the unused child copy cannot affect the Agents tab. Its Subagents index starts empty. Codemode's stored values remain available as of the fork point.

## Isolates

An isolate is where a child's tools run, separate from the parent. Core `host.workspaces` owns the worktree service for subagents and top-level conversations; sandboxes, containers, Cloudflare, and remote machines are not implemented. The authoritative record is the child's `ultimate.workspace` document, exposed as `workspace` in conversation summaries, never duplicated in the Subagents index.

`start {agent, task, isolate?: "none" | "worktree"}` overrides the definition's isolate. The default is none (the shared parent directory); the shipped worker uses worktree. Durable preparation records pending/ready/error before the child starts, on `ultimate/<agent>-<key>` from the parent checkout's HEAD, under the instance home's `worktrees/`. The child's cwd and instructions point there. Uncommitted parent changes are not included. The isolate and child are reused on replay.

Optional project `.ultimate/settings.json` configuration:

```json
{ "isolates": { "worktree": { "setup": ["pnpm install --frozen-lockfile --prefer-offline"] } } }
```

Commands run in order with `sh -c`, closed stdin and a two-minute timeout per command. `ULTIMATE_SOURCE` is the parent checkout path (for example, `cp "$ULTIMATE_SOURCE/.env" .`). A failure reports the output tail and removes only a clean worktree; dirty setup output remains for inspection and explicit cleanup. Setup is recorded so a completed setup is not repeated on replay. A background preparation/admission failure advances the reporter to a durable failure-report checkpoint with a stable task-derived delivery key; it survives reopening, reaches the parent once, and submits no child model input.

Verify the child's commits, then `land {id}`: pins its SHA and fast-forwards the original saved target checkout/branch, requiring both checkouts clean. A moved or diverged target requires explicitly updating the workspace and reverifying first; landing never rebases. An already integrated tip is a no-op. Results list commits and paths, and flag core changes only when landing into the running host checkout. Core `ultimate.workspace-lifecycle` tasks retain foreground tool ownership or run in the calling conversation for UI actions. A session document queues tasks by canonical destination; checks, pinned fast-forward and atomic result recording resume after restart, including cancellation of queued predecessors. Running children/descendants, queued work, preview holds, and overlapping dependent lifecycle operations block mutation. `discard {id}` is explicit, clean-only, refuses active dependent workspaces, and retains the branch and commits. Both operations remain extension actions; `list` includes workspace snapshots. `isolate {parent, id}` returns the authoritative workspace with `ahead` (null once its branch is deleted), or null for a shared child.

Isolation is by working directory, not a sandbox: absolute paths can still reach other checkouts. Children are instructed to work only in their isolate, commit clearly, and never push. There are no remote operations or cross-process landing locks.

The shipped definitions inherit the active provider/model. No universally cheaper model is known across providers, so no model is hardcoded. Override locally to select an available fast model.

The extension document `ultimate.subagents` holds the ownership/action index. Each child gets the core's `ultimate.metadata` (`host.metadata`) with `label` set to its definition's name and `title` to its task, which the shell's header, breadcrumb, and window title show. Reporter request IDs and answer receipts prevent duplicate delivery across restarts; stop records its target run so a replay cannot abort a later run. The action `definitions` returns the definitions (without instructions), the files that failed to parse with their errors, the main conversation's model, thinking level and tools, the user and project folders, and whether the project's setup is local. `definition {name}` returns the definition that applies, its source, path and raw file, the scopes with a file of that name, and a later file of that name that fails to parse. `saveDefinition {name, scope: "project" | "user", frontmatter: {description, model?, thinking?, tools?, isolate?}, instructions, create?}` validates the file as discovery reads it and writes it atomically (`create` refuses an existing name); `deleteDefinition {name, scope}` removes a user or project file.

`web.tsx` renders each `subagent` call (agent, task or message, the child's workspace branch and state from conversation summaries, whether the child is working, its answer, and "open #id" to show the child; the result's details say whether the child is in the background) and adds the right panel's Agents tab: main and its subagents as a tree with working marks and, while a background child works, its `bg` mark from the owner task in the task graph. A child with an isolate shows its state (active, landed with a short sha, or discarded) and commits ahead in its row, and below it the branch with Land and Discard for the parent, disabled while the child runs; Discard asks first, and errors, landing results, and a needed restart show inline. Isolates refetch when the child or parent settles, when the window regains focus, and, while the parent is the shown conversation, as soon as its workspace summary records preparation, land or discard, also one by the `subagent` tool. Below the tree come the definitions with their model and thinking level, and invalid files with their errors, refetched when the window regains focus and when the config dialog closes; each opens its config view (`definitions.tsx`, `fields.tsx`). Showing a child makes the composer steer, follow up, and stop that child; the header leads back to main.
