# cua's Python agent: evaluate, port or skip?

The user asked: "Should we consider both and evaluate? Is there upside in cua's python agent? Could we port what they
implemented at least?"

## Verdict

**Do not run it side by side; port five of its ideas.** `cua-agent` (Python 0.9.1, `libs/python/agent`, ≈28k lines)
is **deprecated by Cua itself**. Its README opens with: _"`cua-agent` is no longer maintained by Cua and will not receive
updates or fixes. For desktop control, connect your coding agent to Cua Driver over MCP."_ Its `omni` extra was
removed because `cua-som` is AGPL and unmaintained. Cua's own direction is what we are building: a coding agent's loop
over Cua Driver.

## Why not a bounded side-by-side evaluation

- **It would compare against a dead end.** The package is unmaintained, and its Computer abstraction predates Cua
  Driver. On the host it acts through the older computer-server path in the foreground (pointer and focus), so it would
  disturb the user and measure a different backend, not a different loop.
- **The setup cost is real:** a Python 3.12 environment, litellm, its own model credentials (it cannot use Ultimate's
  `claude-code` or `openai-codex` providers), a host computer-server install, and telemetry that is on by default.
- **The useful comparison is inside our own loop.** The question that matters is "Jev-first versus frontier-only",
  and phase 5's suite answers it with the same backend, tasks and oracles. That run is cheaper and keeps the result
  actionable.

If the user still wants it, here is a bounded version: the cua agent's Anthropic loop vs ours on the same 10 tasks,
one run each, serial, about 1–1.5 h of the user's desktop taken over, roughly 3–4M input tokens across both arms
(≈$20–50 at Opus-tier prices with caching), plus one hour of setup in an isolated venv (deleted afterwards). Our
recommendation is to skip it.
